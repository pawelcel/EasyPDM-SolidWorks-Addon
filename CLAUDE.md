# Working on EasyPDM for SolidWorks

Conventions that are easy to miss. The EasyPDM server, web app and the Inventor macros live in
[pawelcel/EasyPDM](https://github.com/pawelcel/EasyPDM), the FreeCAD add-on and the drawing
sheet generator in [pawelcel/EasyPDM-FreeCAD-Addon](https://github.com/pawelcel/EasyPDM-FreeCAD-Addon);
each has its own CLAUDE.md.

## Layout

- `EasyPDMUpload.bas`, `EasyPDMDownload.bas` — the macros, the upload and download themselves.
  Their constraints are in comments at the top of each file: ASCII only, CRLF (VBA's "Import
  File" needs both; `.gitattributes` keeps CRLF, CI checks both), declarations before the first
  Sub/Function, late binding (`Object`), WinHttpRequest for binary uploads.
- `Addin/` — the add-in (C#, .NET Framework 4.8, COM). Its commands run the compiled macros
  next to its DLL through `RunMacro2` instead of copying their logic, so the add-in and the
  live-tested macros cannot drift apart. Procedure names it calls (`main`, `LoginInBrowser`,
  `Logout`) and module names (`EasyPDMUpload`, `EasyPDMDownload`) are an interface: renaming one
  in a `.bas` breaks the add-in. What the add-in does itself (the document panel, locking, the
  outdated-component check) talks to the server directly, with the login and server address
  the macros keep in `HKCU\Software\VB and VBA Program Settings\EasyPDM`.
- `EasyPDMSheetFormat.bas` — generated by `tools/build_templates.py --solidworks <this repo>`
  in EasyPDM-FreeCAD-Addon; never edit it here.
- `templates/` — sheet formats and drawing templates, binaries only SOLIDWORKS can write.
  After a sheet layout change, rebuild them with `EasyPDMSheetFormat` on a live SOLIDWORKS and
  commit them. They are linked from release notes, not attached.

## Testing

There is no SOLIDWORKS here, and no automated test of SOLIDWORKS behaviour. CI checks that the
add-in builds without warnings and that the macros are ASCII with CRLF. Everything else is
checked by the user on a live SOLIDWORKS: hand over a test zip (DLL, `install.cmd`,
`uninstall.cmd`, the `.bas` files) and say exactly what to look at. The server side of what
the add-in calls can be checked against a local EasyPDM server.

## Commits, changelog, releases

- Commit messages in English, explaining why the change is right.
- CHANGELOG entries on one line each: the release workflow cuts the section into the GitHub
  release, which renders single newlines as line breaks.
- A release is a `vX.Y.Z` tag equal to `<Version>` in `Addin/EasyPDM.SolidWorks.Addin.csproj`
  (the workflow refuses otherwise). It opens a draft with `EasyPDM_SolidWorks_Addin_vX.Y.Z.zip`.
  The compiled `EasyPDMUpload.swp` / `EasyPDMDownload.swp` need a live SOLIDWORKS: the user
  compiles them, and they go **into that zip** (under `EasyPDM-SolidWorks-Addon/`, replacing
  the draft's asset), not as separate assets: one download holds everything. Check a new
  `.swp` before adding it (an empty one has happened: ~22 KB, no procedure names in
  `strings`). Publishing stays manual.
